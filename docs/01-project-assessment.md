# SmartRoute 项目与市场可行性评估

版本：v0.1
研究快照：2026-08-02

## 1. 执行结论

这个项目有做的必要，但应当作为“可证伪的体验优化实验”立项，而不是一开始就做另一个 Clash 客户端。

更准确的产品定义是：

> SmartRoute 是一个网络环境感知的自适应分流层。它只处理静态规则无法可靠决定的流量，通过 Direct/Proxy 对照观测形成有置信度、会过期、可撤销的本地策略。

建议结论如下：

| 维度 | 评价 | 说明 |
| --- | --- | --- |
| 痛点真实性 | 高 | 规则维护复杂、网络差异真实存在，且现有客户端仍要求用户理解域名、规则类型、优先级和 DNS |
| 技术可行性 | 中高 | TCP/TLS 可做；UDP/QUIC、DNS 因果归因和第一次连接无感切换较难 |
| 产品差异化 | 高 | 已审查的主流方案没有形成“按目标对照探测—学习—持久化—衰减”的系统级闭环 |
| 潜在用户规模 | 中 | Clash/Mihomo 生态很大，但真正受益的是其中的进阶分流用户，不是全部用户 |
| 商业确定性 | 低到中 | 有使用价值不等于有付费意愿，必须通过真实安装和留存验证 |
| 完整客户端成本 | 高 | 跨平台 TUN、权限、更新、签名、内核兼容和 GPL 维护会吞噬大量精力 |
| MVP 投入产出 | 高 | 独立 sidecar + 本地数据库即可验证核心假设 |

因此，项目的 Go/No-Go 判断是：

- **Go：** 做 macOS 优先、TCP/TLS 优先、默认本地处理的实验性 MVP。
- **No-Go：** 现在就 fork Clash Verge Rev 并重做完整客户端。
- **继续投入的条件：** MVP 必须证明端到端延迟、成功率或代理流量中至少有一项显著改善，并且误路由保持在可接受范围内。

## 2. 痛点是否真实存在

### 2.1 真实痛点

现有规则系统需要提前知道答案：某域名、IP、进程或协议究竟应该走哪个出口。公共规则集只能提供一个大致基线，无法覆盖以下变化：

- 不同运营商、地区和网络出口的可达性不同。
- 同一服务的不同子域名可能使用不同 CDN 和访问策略。
- 公司内网、校园网、家庭宽带和手机热点拥有不同的 DNS、IPv6 和路由条件。
- 规则集更新存在滞后，订阅更新还可能覆盖用户手工修改。
- 用户通常只知道“这个网站慢或打不开”，不知道问题在 DNS、IPv4/IPv6、TCP、TLS、代理节点还是服务本身。

Clash Verge Rev 当前已经支持可视化规则和 JavaScript 扩展脚本，但脚本本质上是在配置加载阶段修改静态配置；官方示例仍要求用户理解并编写规则。[Clash Verge Rev 自定义脚本文档](https://www.clashverge.dev/guide/script.html)

用户需求也能在项目反馈中看到：一个 2025 年的功能请求描述了从连接列表找到 host、复制、进入扩展配置、手写规则等一整套操作，并请求一键把连接转为规则。[Clash Verge Rev issue #5491](https://github.com/clash-verge-rev/clash-verge-rev/issues/5491)

这足以证明“规则维护体验差”是真实问题，但还不能单独证明“自动学习”就是最好的解决方案。

### 2.2 哪些用户最痛

优先用户：

- 同时访问境内外服务，代理 RTT 或流量成本明显的用户。
- 在家庭、学校、公司、手机热点之间频繁切换的用户。
- 使用多套订阅或公司 VPN，需要维护局部直连/代理例外的用户。
- 开发者、研究人员和高级用户：目标域名多、第三方 API 多、规则变化快。
- 规则集维护者：希望用真实观测发现规则缺口，而不是只靠人工报告。

收益较弱或不适合作为首批用户：

- 全局代理已经足够快、足够便宜的用户。
- 隐私优先、任何目标都不愿先尝试直连的用户。
- 网络环境非常固定且现有规则已经稳定的用户。
- 主要流量是游戏、实时音视频、QUIC 或其他 UDP 协议的用户。
- 企业强制全隧道、零信任或审计策略禁止动态分流的环境。

### 2.3 痛点强度的诚实判断

这是一个“高频但未必强感知”的问题。用户会感受到网页慢、偶尔打不开、规则麻烦，却未必能直接归因于错误分流。因此产品必须把收益可视化：

- 本周避免了多少次不必要代理。
- 节省了多少代理流量。
- 哪些目标从超时恢复。
- p50/p95 建连或首字节延迟改善多少。
- 哪些决策仍不确定，为什么。

如果只有一个不断增长的自动规则列表，用户很难感知价值，也很难信任系统。

## 3. 已有方案与真实空缺

### 3.1 Mihomo 与 sing-box

Mihomo 的 `url-test` 和 `fallback` 会对预设测试 URL 做健康检查，并选择代理组内的节点；`fallback` 的语义是当前节点不可用时选择第一个可用节点。它们不是针对每个实际目标域名比较 `DIRECT` 和 `PROXY`。[Mihomo URL-Test](https://wiki.metacubex.one/en/config/proxy-groups/url-test/)、[Mihomo Fallback](https://wiki.metacubex.one/en/config/proxy-groups/fallback/)

sing-box 的 `urltest` 同样配置一个测试 URL、周期和候选出站；其路由动作仍是把连接交给指定出站。[sing-box URLTest](https://sing-box.sagernet.org/configuration/outbound/urltest/)、[sing-box Rule Action](https://sing-box.sagernet.org/configuration/route/rule_action/)

这些能力解决的是“哪个代理节点可用/更快”，而 SmartRoute 解决的是“这个具体目标是否应该代理”。两者互补。

### 3.2 Clash Verge Rev

Clash Verge Rev 是基于 Tauri、内置 Mihomo 的跨平台 GUI，支持系统代理、TUN、配置增强和规则编辑。[Clash Verge Rev 仓库](https://github.com/clash-verge-rev/clash-verge-rev)

它可以成为最终 UI 基座，但有三个边界：

- 扩展脚本处理配置，不位于每条连接的数据路径上。
- 未主动启用 External Controller 时，当前版本使用私有 IPC 与内核通信；项目维护者明确表示不为该 IPC 提供外部自动化支持，需要控制内核时应显式启用 External Controller。[官方讨论 #6951](https://github.com/clash-verge-rev/clash-verge-rev/discussions/6951)
- 修改并分发该项目需要遵守 GPL-3.0，且要持续承担三平台打包、签名、权限和上游同步成本。

因此，直接 fork GUI 并不能解决关键的数据面能力。

### 3.3 浏览器扩展

SmartProxy 支持按模式自动启停代理，并允许用户查看当前页面请求、一键把站点加入代理列表；它限定在浏览器层，主要仍由用户确认规则。[SmartProxy 仓库](https://github.com/salarcode/SmartProxy)

ZeroOmega/SwitchyOmega 提供多代理配置、自动切换条件和 PAC 生成，但其核心仍是条件匹配与配置管理，而不是持续对照学习。[ZeroOmega 仓库](https://github.com/zero-peak/ZeroOmega)

这些项目说明“降低分流配置门槛”有用户需求，也为 SmartRoute 提供了交互参考。

### 3.4 竞争结论

截至本次调研，在审查的官方文档、主流项目和相关仓库中，没有发现一个主流系统级工具完整实现：

```text
未知目标进入观察
→ Direct/Proxy 同期对照
→ 区分失败阶段
→ 按网络环境积累置信度
→ 自动形成可撤销、会过期的策略
→ 持续复验和修正
```

这不是“世界上绝对不存在”的证明，只能说明在本次检索范围内存在清晰的产品空位。

## 4. 是否真的能够提升体验

### 4.1 能改善的部分

- 对可稳定直连但被宽泛规则送去代理的目标，减少额外 RTT、代理拥塞和带宽消耗。
- 对静态规则漏掉的受限目标，在短暂探测后恢复访问，并在后续连接直接使用正确路径。
- 在网络切换后加载对应的局部策略，减少手工改规则。
- 把“打不开”拆成 DNS、TCP、TLS、代理节点或服务端问题，提升可诊断性。

### 4.2 不能保证改善的部分

- 代理路径可能比直连更快；“能直连”不自动等于“直连体验更好”。
- 公共规则已命中的大部分热门域名不会产生额外收益。
- 第一次访问未知且受限的目标仍可能承担一个短暂的探测窗口。
- UDP 没有通用握手成功信号，QUIC 和游戏场景第一版难以无感回退。
- 应用已经发送业务数据后，透明地换路并重放可能造成重复操作，不能通用实现。
- 同一站点通过 Direct 与 Proxy 可能获得不同地区内容、风控结果或账号状态。

### 4.3 体验收益的简单模型

对一个未知 TCP 目标：

```text
静态代理耗时       ≈ L_proxy
串行直连失败再代理 ≈ T_direct_timeout + L_proxy
错峰竞争首次耗时   ≈ min(L_direct, head_start + L_proxy)
学习后的耗时       ≈ 已知优选路径耗时
```

因此不能等待系统 TCP 超时后再代理。更合理的是让 Direct 获得短暂领先窗口，再启动 Proxy 候选。Happy Eyeballs 在 IPv4/IPv6 选择上采用类似思想，RFC 8305 给出的默认连接尝试间隔参考值是 250ms，但 SmartRoute 的值应通过真实网络数据校准，而不是照搬。[RFC 8305](https://datatracker.ietf.org/doc/html/rfc8305)

## 5. 产品定位与用户承诺

### 5.1 一句话定位

> 让代理规则从“别人替你写死的名单”变成“在你的网络里持续验证、能够解释和撤回的本地策略”。

### 5.2 不建议使用“AI 代理”作为第一卖点

第一版不需要模型。迟滞状态机、指数衰减、Beta-Bernoulli 可靠度估计就足够。称为“AI”会提高用户对准确率的预期，却不能消除网络观测本身的歧义。

更合适的卖点是：

- 自适应分流
- 本地学习
- 可解释路径诊断
- 网络环境隔离
- 一键撤销与锁定

### 5.3 隐私承诺

- 默认只在本地保存。
- 默认不上传域名、进程名或浏览历史。
- 敏感域名和用户锁定目标从第一次起仅走代理，不做直连探测。
- UI 清楚显示哪些目标曾被直连探测。
- 数据可导出、可清空、可设置保留期。
- 云端众包只能是后续显式 opt-in 功能，不能是 MVP 的依赖。

## 6. 市场与开源策略

Clash Verge Rev 仓库在调研时显示约 13.4 万 GitHub stars，浏览器层的 SmartProxy 和 ZeroOmega 也分别显示约 2.7k 和 7.7k stars。这些数字只能证明代理管理和分流工具拥有活跃用户群，不能直接推导 SmartRoute 的安装量或付费率。[Clash Verge Rev](https://github.com/clash-verge-rev/clash-verge-rev)、[SmartProxy](https://github.com/salarcode/SmartProxy)、[ZeroOmega](https://github.com/zero-peak/ZeroOmega)

建议的早期分发策略：

- 开源、免费、本地优先，先获取可信使用数据和问题反馈。
- 与 Mihomo 配置兼容，不绑定机场或节点供应商。
- 先服务高级用户，提供明确的诊断记录和导出能力。
- 如果后续商业化，优先考虑托管规则同步、团队策略、跨设备网络画像和企业可观测性，而不是出售代理节点。

需要特别注意：分发或商业化网络代理软件在不同司法辖区可能涉及合规要求；GPL 派生关系、商标/命名和应用签名也应在发布前单独审查。本设计不构成法律意见。

## 7. 最终立项建议

### 应该做

- 一次 4–8 周、目标和退出条件明确的核心可行性 MVP；通过后再增加 2–4 周小范围试用。
- 先做 Shadow Mode 和可量化基准。
- 先做 TCP/TLS、完整域名、单机、本地数据库。
- 把“解释为什么这样选”作为一等功能。

### 暂时不要做

- 从零实现 TUN、DNS 和代理协议。
- 一开始支持全部 UDP/QUIC。
- 一次失败就生成永久域名后缀规则。
- 默认上传匿名域名统计。
- 在核心收益未验证前维护完整 Clash Verge Rev fork。

### 一票否决条件

满足任一条件就停止扩大投入：

- 相比优质静态规则基线，p95 体验没有可重复改善。
- 为减少少量代理流量而显著增加首访失败或抖动。
- 误判需要用户频繁手工修复。
- 直连探测带来的隐私顾虑使目标用户不愿开启。
- 跨平台集成成本远高于核心算法产生的价值。
